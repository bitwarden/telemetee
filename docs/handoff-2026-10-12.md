## What this is

An anonymizing telemetry collector for Bitwarden clients, hosted in a Confidential ACI container
(AMD SEV-SNP) that clients verify by attestation before sending anything. The adversary is Bitwarden
itself, including its CDN. The attack to block is CDN-side targeting of a user combined with
collector-side observation of that user's response; breaking the collector side is the goal. OHTTP
on the CDN and collector is planned separately and is what removes client identity from the send.

Design points settled in conversation:

- Stateless: no persisted state, nothing shared across builds. In-memory process-lifetime state
  (Noise static key, pseudonymization salt, batch buffer) is allowed.
- Clients ship a hardcoded pin table `collector version -> hostdata` in open-source client code.
  Supported collector versions run concurrently, one container group each, routed by the version
  segment in `/<version>/…`. Monthly client cadence. A transparency-logged allowlist (Rekor or
  similar) is the documented future path to decoupling cadences, and is also the clean fix for the
  separate open question about the generated Rego — whether to enumerate the TCB inline
  (`--exclude-default-fragments`, worm-safe hash, support window bounded by MS infra churn on
  restart) or defer part of it to Microsoft's signed infrastructure fragment (hash survives MS
  updates, trust surface widens to the fragment's issuer/feed/minSVN). Both choices are bridges to
  the log: once clients verify "hostdata ∈ log" instead of pinning a fixed set, new hostdatas
  (code change, periodic reattestation, or MS-forced regeneration) become log entries under a
  review workflow, and old entries stay valid as long as the matching container group is runnable.
- Clients pin a Microsoft shared attestation provider (no customer policy possible), check
  `sevsnpvm`, `azure-compliant-uvm`, `is-debuggable == false`, hostdata, and take the collector's
  Noise static key from `x-ms-runtime.noise_pub`.
- Noise NK over HTTP, suite `Noise_NK_P256_AESGCM_SHA256`: .NET 10's BCL has ECDH P-256, AES-GCM,
  and SHA-256 but no X25519 or BLAKE2s, and the SDK's `bitwarden-ipc` already runs these
  primitives. Message 1 carries the request payload, message 2 the reply; no transport phase.
- Fixed-size padded pages, client flushes on its own clock, holds overflow, no dummy pages when
  empty. Cover traffic deferred, with the accurate reasoning recorded: the edge still learns that a
  client had something to report in a tick.
- Collector batches in memory with shuffled order and batch-level timestamps, forwards directly to
  Datadog. Anonymization is a per-field schema (`drop`, `keep`, `bucket`, `pseudonymize`) in the
  attested code. Not built yet.
- No default OpenTelemetry: per-request spans carry arrival time and user agent. Only an explicit
  aggregate meter `Bitwarden.Telemetee` is exported, with a 60 s floor on export interval that must
  stay above the batch window.

## State of the code

Milestone 1 (attested Noise channel) is complete and verified locally; not yet deployed.

- `src/Telemetee.NoiseChannel`: NK responder from the Noise spec over BCL crypto, static key as
  `INoiseStaticKey`, `POST echo`, `telemetee.pages` counter. Internal initiator for tests.
- `src/Telemetee.Attestation`: `SidecarAttestationTokenSource` (`POST /attest/maa` on
  `mcr.microsoft.com/aci/skr`), token provider that embeds `{"noise_pub": …}` and refreshes ahead
  of `exp`, `GET attestation`, `telemetee.attestation.refreshes` counter, and a development issuer
  that mints MAA-shaped RS256 tokens with a JWKS in MAA's `kid` + `x5c` format.
- `src/Telemetee.Collector`: ASP.NET Core minimal API host on `Bitwarden.Server.Sdk` 1.7.0 with
  authentication, feature flags, and SDK telemetry compiled out; listens on 5000 because the
  sidecar owns 8080 in the shared network namespace.
- `crates/telemetee-client`: MAA token verification (`jsonwebtoken` + `x509-parser` for x5c-only
  JWKS), `NkInitiator` over `snow` with `bitwarden-random::SdkCryptoResolver` path-linked from
  `../sdk-internal`, `CollectorClient`. `crates/telemetee-cli` wraps it.
- Tests: 28 .NET (xunit, `WebApplicationFactory`, `MetricCollector`), 12 Rust. End-to-end verified
  with the CLI against the collector in Development mode: handshake interop between `snow` and the
  C# responder, token verified through the x5c path, wrong hostdata and wrong issuer rejected.
- `deploy/`: ARM template (collector + sidecar pinned by digest, confidential SKU, optional
  registry credentials), `build-image.sh` (reproducible build), `generate-policy.sh` (pinned
  confcom, decoded policy, wildcard allowlist check), `allowed-wildcards.txt`, `README.md` with the
  deployment steps, secrets rules, and audit procedure.
- `.github/workflows/build.yml`: dotnet, rust, a two-build reproducibility check, and a
  tag-triggered release that pushes by digest and publishes template, `policy.rego`, hostdata, and
  allowlist.

Verified facts about the build:

- `dotnet publish` output is byte-identical across builds; only Docker layer timestamps differed.
  With digest-pinned bases, `SOURCE_DATE_EPOCH`, and `rewrite-timestamp` through a
  `docker-container` BuildKit builder, two builds give the same image ID and the same hostdata.
  The default `docker` driver silently ignores `rewrite-timestamp`.
- confcom 2.3.0 from nixpkgs works once the flake sets the executable bit on its bundled
  `dmverity-vhd` (done in `~/code/flakes/telemetee/flake.nix` via `overrideAttrs` inside
  `azure-cli.withExtensions`). The nix `az` cannot pip-install extensions.
- Decoded policy for the current template: no infrastructure fragment, no exec processes, no `id`
  fields, three containers, four env vars pinned to literals.

## Rules established

- Every env var in the template is pinned into the policy. Literals are embedded verbatim, so a
  secret must be an ARM parameter with no default (`securestring`, `secureValue`), which confcom
  turns into `NAME=.*`. Every such wildcard is an operator-controlled input to attested code and
  must be in `deploy/allowed-wildcards.txt`; endpoints, environment names, and behavioural settings
  stay literal. `ASPNETCORE_ENVIRONMENT` in particular must never be a wildcard, since
  `Development` turns on the dev token issuer.
- Parameters with a `defaultValue` are pinned; parameters without one become wildcards.
- The hostdata clients pin must come from the release workflow, but anyone must be able to
  reproduce it from the tagged source: `deploy/build-image.sh` then `deploy/generate-policy.sh`.
- Metrics must be derivable from what an observer already sees (edge: request counts and timing;
  sink: batch sizes) and never joinable to a single request.

Once registered, follow `deploy/README.md` steps 1 to 5. The experiments it answers:

- Does the container group start with `--exclude-default-fragments`? If not, rerun with
  `EXCLUDE_DEFAULT_FRAGMENTS=0`.
- Does `x-ms-runtime` carry `noise_pub` as parsed JSON on a real token (expected yes).
- Does a shared provider accept attest calls with no bearer token (expected yes).
- Token lifetime (`exp - iat`, expected 8 h).
- confcom hostdata stability across machines (CI will show).

`UVM_HOST_AMD_CERTIFICATE`), TLS in front of the collector, telemetry schemas, padding, batching,
the Datadog sink, `telemetee.batch.*` metrics, SDK integration and client pin tables, moving the
client crate into `sdk-internal`.
